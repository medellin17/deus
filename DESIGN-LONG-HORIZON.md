## 0. TL;DR

Deus уже умеет: гонять детерминированные пайплайны, проверять результат настоящими командами проекта, изолировать прогон в git worktree, вливать изменения, вести доску задач, будить ведущего и возвращать задачу на доработку.

Для задач на десятки и сотни часов этого мало. Не хватает трёх вещей:

1. **Верхнего якоря** — контракта миссии: что должно стать правдой, что нельзя ломать, как поймём, что готово, какие допущения ещё не проверены и что агент вправе решать сам.
2. **Коридора отклонений** — правила, по которому локальные отклонения продолжаются без остановки, кросс-граничные требуют checkpoint, а нарушение контракта останавливает работу.
3. **DAG в двух слоях** — параллельный read-only fan-out в пайплайне и параллельные change-задачи на доске с отдельными worktree и последовательным merge.

Ключевая мысль: **конституция, а не карта**. Контракт и инварианты постоянны, архитектура и план — сменные гипотезы. Дрейф меряем не по расстоянию до плана, а по нарушению контракта.

## 1. Задача документа

Ответить на вопросы:

- что уже есть в deus и чего не хватает для длинных задач;
- на каком уровне закреплять «что нужно» и почему не на архитектурном;
- как выглядит полный цикл: замысел → recon → варианты → решение → план → исполнение → контроль дрейфа → ретро;
- какие отклонения допустимы и когда останавливаться;
- как устроен DAG, что можно параллелить, а что нельзя;
- что меняется при переходе от 1–8 часов к 10–40 и к 100+ часам;
- в каком порядке это строить и по каким критериям принимать.

Документ не является детальным планом кода. Для каждого кирпича пишется отдельный `plan-*.md` с DoD, тестами и рисками.

### 2.1. Что уже работает

| Авто-мерж и разрешение конфликтов | `src/v2/apply.ts`, `gitflow.ts` | `--no-ff`, откат, проверка после merge |
| Permission-политика | `src/v2/permissions.ts` | Предохранители, не песочница |
| Чекпоинты и `--resume` | `src/v2/pipeline.ts`, `store.ts` | Состояние после каждого шага |
| Доска задач | `src/v2/board.ts` | SQLite, статусы, CAS-аренда, `depends_on`, события |
| Кодинговая команда | `src/v2/team.ts` | Параллельные задачи, свой worktree на задачу, serial merge |

| Авто-лид | `src/v2/lead.ts` | Советник без инструментов: `rework` или `escalate` |

| Адресные сессии | `src/v2/sessions.ts` | `followUp` в существующую сессию |

### 2.2. Что мешает длинным задачам

| Ограничение | Факт | Последствие |
|---|---|---|
| План линейный | `PlanStep` не имеет `dependsOn`; `runPipeline` идёт `for (const step of state.plan)` | Нет fan-out, нет join, нет параллельного recon |
| Планировщик ограничен 8 шагами | `MAX_STEPS = 8` в `planner.ts` | На 100 часов не хватит; нужна иерархия milestone → tasks |
| Нет контракта миссии | `deus.json` — конфиг проекта, а не задачи | Агент не знает non-goals, инвариантов и acceptance, кроме текста задачи |
| Нет классов отклонений | Авто-лид умеет только `rework`/`escalate` | Любое отклонение либо пропускается, либо останавливает всё |
| Нет drift-лога | В `run.json` есть шаги и стоимость, но не отклонения | Нельзя восстановить, почему решение уехало |
| Gate синхронный | `spawnSync` в `gate.ts` | Блокирует event loop; параллельные задачи получают ложный таймаут |
| HTTP без таймаутов | `session.get`/`prompt` не получают `RequestOptions.signal` | Полуоткрытое соединение вешает процесс с занятым lock |
| Потолок стоимости инертен | `estimateCost` возвращает 0 для неизвестной модели | `--max-cost` не срабатывает на дефолтной бесплатной модели |
| Доска ограничена 1000 задач | `selectReadyTasks` использует `limit: 1000` | Задача №1001 молча не берётся |
| Нет иерархического плана | Плоский список шагов | Контекст одного плана растёт, milestone-границы не выражены |
| Нет steward | Авто-лид не умеет `continue-with-note` и `replan` | Коридор отклонений некому применять |

### 2.3. Статусы фактов

- **ПОДТВЕРЖДЕНО кодом:** линейный план, `MAX_STEPS = 8`, `spawnSync`, отсутствие `signal` в клиентских вызовах, `estimateCost → 0` для неизвестной модели, `limit: 1000`, наличие `depends_on` и CAS на доске.
- **ПОДТВЕРЖДЕНО документацией проекта:** авто-лид умеет только `rework`/`escalate`; 420 тестов, `typecheck` 0, `v2:smoke` ok — по записям в `.context/next-steps-deus.md`, сам не перепроверял.
- **ГИПОТЕЗА:** предложенная здесь архитектура контракта, коридора и двухслойного DAG. Её нужно проверить пилотом на 10–40-часовой задаче до того, как строить 100-часовой режим.

## 3. Принципы

1. **Конституция, а не карта.** Контракт и инварианты постоянны. Архитектура и план — гипотезы, которые обязаны меняться при новых фактах.
2. **Контракт раньше архитектуры.** Архитектура до recon — догадка. Закреплять её как верхний уровень — значит либо ломать при первом открытии, либо врать.
3. **Доказательства раньше мнений.** Acceptance без evidence — это мнение. Recon без `file:line` или вывода команды — это пересказ.
4. **Один писатель на дерево.** Два агента не правят один worktree. Параллельные правки — только через отдельные деревья и последовательный merge.
5. **Бюджет жёсткий, дрейф видимый.** Любое отклонение класса D2+ попадает в drift-лог. Любой лимит либо не срабатывает, либо виден в отчёте.
6. **Планы одноразовые, инварианты постоянные.** План можно переписать. Контракт нельзя.
7. **Человек владеет целью, агент — способом.** Агент предлагает варианты и рекомендацию. Цель, non-goals, acceptance и бюджеты утверждает человек.
8. **Front-load uncertainty.** Чем длиннее задача, тем дороже поздняя ошибка. Основные деньги на recon и варианты тратятся в начале.
9. **Никаких тихих отклонений.** D2+ всегда с записью: что, почему, альтернативы, цена, затронутый acceptance.
10. **Остановка только на контракте или необратимом.** Внутри коридора работа продолжается. D4 — стоп, D3 — checkpoint, D1–D2 — вперёд.

## 4. Уровни, на которых живёт длинная задача

| Уровень | Что там | Кто меняет | Артефакт | Срок жизни |
|---|---|---|---|---|
| L0 Миссия | зачем, какой исход, чего точно не надо | человек | 5–10 строк в `mission.md` | вся миссия |
| **L1 Контракт** | инварианты, acceptance, допущения, бюджеты, права | человек утверждает; агент только предлагает | `mission.json` | вся миссия, версии |
| L2 Архитектура | модули, интерфейсы, поток данных | архитектор в рамках контракта | `adr.md` | до следующего ADR |
| L3 План/DAG | задачи, зависимости, порядок | планировщик/раннер | `plan.json` | один milestone или волна |
| L4 Исполнение | сессии, worktree, команды | executor/доска | `run.json` | один прогон |
| L5 Доказательства | gate, diff, логи, стоимость | никто не редактирует | артефакты прогона | вся миссия + retention |

Только L0–L1 меняет человек. L2–L4 агент меняет свободно, пока не нарушает L1. L5 — истина, её нельзя переписать.

### Почему не архитектура

Архитектура — первая производная от контракта. Если закрепить её как верхний уровень, то при первом же открытии (библиотека не та, API изменился, зависимость сломалась) придётся либо ломать архитектуру, либо подгонять факты. Контракт переживает смену архитектуры; архитектура не переживает смену контракта.

### Почему не план

План — самая хрупкая сущность. Он ломается от первого нового факта. Если план — закон, агент либо тупо следует устаревшему плану, либо молча отклоняется. Оба варианта хуже коридора.

## 5. Контракт миссии

### 5.1. Что это

`mission.json` — машинно-проверяемый контракт одной миссии. `mission.md` — человеческое объяснение: зачем, контекст, отвергнутые варианты, риски, открытые вопросы. JSON не дублирует MD; MD ссылается на JSON и объясняет «почему».

Контракт живёт в `.deus/missions/<mission-id>/`:

```
.deus/missions/<mission-id>/
├── mission.json      # машинный контракт + approval + hash
├── mission.md        # замысел, контекст, риски, открытые вопросы
├── recon.md          # факты и проверенные допущения
├── options.md        # варианты и сравнение
├── adr.md            # решение и причины
├── drift.md          # отклонения D2+
└── retro.md          # уроки и обновления инвариантов
```

Прогон ссылается на миссию и её хеш: `run.json.mission = { id, version, hash }`. Если хеш не совпадает с текущим файлом, `--resume` отказывает: контракт изменился, продолжать вслепую нельзя.

### 5.2. Поля

| Поле | Обязательно | Смысл |
|---|---|---|
| `version` | да | версия схемы контракта |
| `id`, `title` | да | идентификатор и короткое имя |
| `goal` | да | исход, а не активность: «после запуска проект читает новый формат» |
| `non_goals` | да | что точно не делаем; защита от расширения скоупа |
| `invariants` | да | что должно оставаться истинным всегда; по возможности проверяемо |
| `acceptance` | да | список `{ id, check, evidence, manual? }`; без evidence пункт не считается |
| `assumptions` | да | `{ id, text, status, load_bearing, evidence }`; статус `verified`, `unverified`, `risk` |
| `budgets` | да | `max_cost_usd`, `max_hours`, `max_attempts_per_task`, `max_tasks`, `max_waves` |
| `decision_rights` | да | что решает человек, что агент |
| `deviation_policy` | да | действие по умолчанию для D1–D4 |
| `checkpoints` | да | где останавливаемся: after_recon, after_options, before_first_change, milestone, budget_50, budget_80 |
| `protected_surfaces` | да | `.git`, `.deus`, `.env*`, ключи, публичные API, схема БД |
| `workspace` | да | `allow`/`deny` по путям; сужает права агента |
| `open_questions` | нет | что ещё не решено и кто решает |
| `approval` | да | кто, когда, версия, хеш |

### 5.3. Пример

```json

  "id": "mission-2026-11-23-config-loader",
  "title": "Перевести загрузчик конфигов на новый формат",
```

### 5.4. Правила

1. **Контракт короткий.** Goal, non-goals, acceptance, инварианты — на один экран. Если контракт не помещается, его никто не будет читать, включая агента.
2. **Acceptance только с evidence.** `check` — команда или ручная проверка; `evidence` — что именно доказывает. Ручной пункт помечается `manual: true`.
3. **Допущение с `load_bearing: true` и `status: "unverified"` блокирует первый change-шаг.** Оно либо проверяется recon-ом, либо становится D3-checkpoint. Это главная защита от дрейфа.
4. **Контракт не пишет сам себе агент.** Агент может подготовить черновик и предложить поправку. Утверждает человек, ставит `approval`.
5. **Любое изменение контракта — новая версия.** Меняются `version`, `approval`, хеш. Прогон с другим хешем не продолжается без явного решения.
6. **Агент не может расширить права.** `workspace` и `protected_surfaces` только сужают то, что разрешено сервером и политикой.
7. **Mission ≠ project config.** `deus.json` остаётся конфигом проекта: checks, model, лимиты. `mission.json` — про одну задачу или одну долгоживущую команду.

### 5.5. Изменение контракта в середине миссии

- Агент пишет `mission-amendment` с причиной, evidence и последствиями.
- Раннер ставит миссию на паузу в ближайшем checkpoint.
- Человек approves или rejects. При approve — новая версия, пересчёт acceptance, инвалидация затронутых задач.
- При reject — миссия продолжается по старой версии; amendment остаётся в ADR как отвергнутый.
- Автоматического принятия изменений контракта нет. Это D4 по определению.

## 6. Жизненный цикл длинной задачи

| Этап | Кто | Вход | Выход | Ворота |
|---|---|---|---|---|
| 0. Замысел | человек + агент-редактор | 5–10 строк | черновик `mission.md`, список допущений | — |
| 1. Контракт | человек | черновик | утверждённый `mission.json` + `mission.md`, хеш | human approval |
| 2. Recon | 3–5 read-only агентов параллельно | контракт | `recon.md`: факты, ограничения, тестовое поле, риски | after_recon |
| 3. Варианты | 2–3 агента с разными линзами | recon | `options.md`: 2–3 подхода, цена, риск, обратимость | after_options |
| 4. Решение | синтез + человек на D3 | options | `adr.md`: выбранный подход, отвергнутые, residual risks | human if D3 |
| 5. План | планировщик | ADR + контракт | `plan.json`: milestone → tasks, deps, acceptance | before_first_change |
| 6. Исполнение | доска + воркеры | план | worktree, diff, gate, merge, `run.json` | gate + post-gate |
| 7. Steward | советник без инструментов | drift, gate, cost | `continue` / `rework` / `replan` / `escalate` | каждый gate + бюджетные пороги |
| 8. Ретро | человек + агент | вся миссия | `retro.md`, обновление инвариантов | конец milestone / миссии |

### 6.1. Замысел

Человек говорит общими словами. Агент-редактор задаёт только вопросы, которые меняют реализацию: кто пользователь, что считается успехом, что нельзя ломать, какие ограничения по времени и деньгам. Выход — не план, а черновик контракта и список допущений.

### 6.2. Recon

Параллельные read-only агенты, у каждого своя линза:

- **Кодовая база:** где точка входа, какие модули затронуты, какие тесты уже есть.
- **Ограничения:** зависимости, версии, CI, линтеры, формат коммитов.
- **Тестовое поле:** что уже покрыто, какие проверки можно запустить, где baseline красный.
- **Риски:** что может сломаться, какие допущения не проверены, где секреты.
- **Альтернативы:** как это уже решено в проекте или в похожих местах.

Каждый факт — с `file:line` или выводом команды. Без доказательства — это гипотеза, и она идёт в `assumptions`, а не в `recon.md` как факт.

### 6.3. Варианты

2–3 независимых агента, каждый со своей линзой:

- **Минимальный:** наименьший diff, наименьший риск, может быть некрасиво.
- **Надёжный:** правильные границы, тесты, обработка ошибок, больше времени.
- **Купить/не делать:** существующая библиотека, внешний сервис или отказ от задачи.

Агенты не видят ответы друг друга до синтеза. Иначе получится три копии одного варианта. Каждый вариант обязан назвать: цену, риск, обратимость, затронутые инварианты и что должно быть правдой, чтобы он сработал.

### 6.4. Решение

Синтез строит матрицу сравнения по критериям из контракта. Если критериев нет, это D3: человек добавляет критерии, а не агент придумывает их сам. В `adr.md` фиксируются:

- выбранный вариант и почему;
- отвергнутые варианты и почему;
- residual risks;
- что изменит решение (falsification criteria);
- какие допущения всё ещё не проверены.

### 6.5. План

Двухуровневый:

```
Миссия
├── Milestone 1 (3–7 задач)
│   ├── task 1 (analyze) ──┐
│   ├── task 2 (analyze) ──┼──> join
│   └── task 3 (change)
├── Milestone 2
│   ├── task 4 (change) ──> gate
│   └── task 5 (review)
└── Milestone 3 ...
```

- **Milestone** — крупная граница с собственным acceptance-подмножеством и бюджетом. Обычно 3–7 на миссию.
- **Task** — единица доски с зависимостями, workspace, acceptance и бюджетом. Обычно 5–20 на milestone.
- Плоский лимит 8 шагов остаётся только для одной волны, не для всей миссии.

### 6.6. Исполнение

- Задачи берутся с доски через CAS.
- Каждая change-задача — свой worktree и своя ветка.
- Gate идёт до коммита; merge сериализован; после merge — повторный gate в одноразовом дереве.
- Параллельность ограничена `--team-parallel`; merge всегда один.
- Волна заканчивается, когда ready-set пуст или сработал бюджет/abort.

### 6.7. Steward

См. раздел 7. Steward не заменяет gate и не принимает задачи. Он решает, что делать с отклонением: продолжить, вернуть, перепланировать или позвать человека.

### 6.8. Ретро

В конце milestone или миссии:

- какие допущения оказались неверными;
- какие отклонения были D2/D3 и почему;
- что нужно добавить в инварианты;
- какие проверки стоит автоматизировать;
- что упростить в следующий раз.

Ретро обновляет контракт (новая версия) и, при необходимости, шаблон миссии.

## 7. Коридор отклонений

### 7.1. Классы

| Класс | Что это | Пример | Действие по умолчанию |
|---|---|---|---|
| **D1** | локальная реализация | другой цикл, другой helper, другой порядок вызовов внутри той же задачи | продолжить, записать в drift-лог |
| **D2** | локальный дизайн | новый внутренний модуль/интерфейс внутри задачи, без внешних эффектов | продолжить, записать, перепроверить acceptance, добавить ADR-addendum |
| **D3** | кросс-граница | новая зависимость, схема БД, публичный API, чужая задача/workspace, protected surface, стоимость выше порога | checkpoint: пауза ветки, варианты, решение человека или заранее разрешённое правило |
| **D4** | контракт | меняет goal/non-goal/acceptance; необратимое действие (push, удаление данных, миграция, force); нарушение безопасности | стоп, эскалация |

**Дрейф меряем не по расстоянию до плана, а по нарушению контракта.** Заменить план, переставить задачи, выбрать другую внутреннюю структуру — это не дрейф. Дрейф — это когда меняется то, что должно остаться правдой, или когда работа уходит за границы, которые человек считал фиксированными.

### 7.2. Где проверяем

- после recon: все ли load-bearing допущения проверены;
- после options: не изменились ли критерии выбора;
- перед первым change: контракт утверждён, acceptance привязан к проверкам;
- на каждом gate: diff не трогает protected surfaces, acceptance не подменён;
- на merge: ветка не меняет чужие workspace, post-gate зелёный;
- на 50% бюджета: обязательный обзор скорости и скоупа;
- на 80% бюджета: новый скоуп запрещён, только завершение или эскалация;
- на 100%: стоп.

### 7.3. Steward

Steward — советник **без инструментов**, как авто-лид, но с другим набором решений:

| Решение | Когда | Что делает раннер |
|---|---|---|
| `continue` | D1, всё в коридоре | продолжает, пишет строку в drift-лог |
| `continue-with-note` | D2, локальный дизайн | продолжает, добавляет note в ADR и следующий промпт |
| `rework` | задача не прошла gate или review | возвращает в backlog с замечанием |
| `replan` | план перестал соответствовать фактам, но контракт цел | строит новый план в рамках миссии, инвалидирует затронутые задачи |
| `escalate` | D3 без заранее разрешённого правила или D4 | останавливает ветку/миссию, готовит пакет человеку |

Правила:

- Steward видит mission, plan, drift-лог, вывод gate, diff-статистику, стоимость и прошлые замечания. Он **не** видит весь репозиторий и не имеет инструментов.
- Steward не может принять задачу: `accept` требует настоящего gate.
- Steward не может изменить контракт. Только предложить amendment.
- Невалидный ответ Steward (мусор, несколько объектов, пустая заметка) → `escalate`, а не `continue`.
- `replan` ограничен: не больше N раз на milestone; каждый replan сохраняет acceptance и фиксируется в ADR.
- Стоимость Steward входит в бюджет миссии.

### 7.4. Эскалационный пакет

Чтобы человек не тратил час на восстановление контекста, Steward готовит короткий пакет:

```json
{
  "mission": "mission-2026-11-23-config-loader",
  "kind": "D3",
  "what_changed": "понадобилась зависимость yaml-v2",
  "why": "стандартный парсер не поддерживает якоря",
  "options": [
    { "id": "A", "text": "добавить yaml-v2", "cost": "$0", "risk": "новая зависимость" },
    { "id": "B", "text": "написать мини-парсер", "cost": "2 дня", "risk": "свой баг" },
    { "id": "C", "text": "сузить формат", "cost": "0", "risk": "ломает прод-конфиг" }
  ],
  "recommendation": "A",
  "budget_spent": "$0.84 из $2.50",
  "blocked_tasks": ["bt-..."],
  "deadline": "2026-11-23T18:00:00Z"
}
```

Если человек не ответил до deadline, ветка остаётся `blocked`, независимые ветки продолжаются. Автоматического «разрешаю на всякий случай» нет.

### 7.5. Бюджетные пороги

| Порог | Что происходит |
|---|---|
| 50% | обязательный checkpoint: скорость, остаток, скоуп, прогноз |
| 80% | новый скоуп запрещён; только завершение текущего или эскалация |
| 100% | стоп; незавершённые задачи остаются в `blocked`/`review`, отчёт человеку |

Порог считается по стоимости, времени и числу волн — что наступит раньше. Если цена модели неизвестна, а `max_cost` задан, миссия не стартует: неизвестная цена — не ноль.

## 8. DAG

### 8.1. Два слоя

| Слой | Что параллелим | Изоляция | Где живёт | Когда |
|---|---|---|---|---|
| **Pipeline DAG** | read-only: recon, options, audit, review | один worktree, только чтение | `plan.json` + `pipeline.ts` | кирпич 2 |
| **Board DAG** | change-задачи | свой worktree на задачу, serial merge | `board.db` + `team.ts` | кирпич 3 |

Почему не один слой: параллельные change-шаги в одном worktree — это не параллелизм, а генератор конфликтов. Два агента, правящих один файл, всё равно требуют интерфейса, который надо зафиксировать до старта. Такой интерфейс — уже отдельный milestone, а не DAG-узел.

### 8.2. Схема узла

```ts
interface PlanNode {
  id: string;                    // kebab-case, уникальный
  agent: string;                 // только из живого списка
  mode: "analyze" | "change";
  task: string;                  // конкретная инструкция
  dependsOn: string[];           // id родителей
  acceptance?: string[];         // id из mission.acceptance
  workspace?: { allow: string[]; deny: string[] };
  budget?: { maxCostUsd?: number; maxSteps?: number };
  join?: "concat" | "synthesize"; // как объединить родителей
  timeoutSeconds?: number;
}
```

Валидация:

- id уникальны, kebab-case, до 40 символов;
- `dependsOn` существуют, без циклов и самозависимостей;
- агент только из списка, который вернул сервер;
- `analyze` не получает edit/shell/subagent;
- `change` не может быть параллелен другому `change` в pipeline-слое;
- если есть `change`, последний узел (или явный review-узел) — `analyze`;
- каждый `change` имеет acceptance или наследует mission acceptance;
- никаких новых агентов, прав или permission-правил из плана.

### 8.3. Планировщик

1. Валидирует граф и строит карту зависимостей.
2. Ready-set = узлы, у которых все родители `succeeded`.
3. `analyze`-узлы запускаются волной параллельно до `parallel` cap.
4. `change`-узлы запускаются по одному; после каждого — gate и коммит.
5. Join ждёт всех родителей, затем `concat` или synthesis-агент.
6. Успех узла: сохранить состояние, артефакт, стоимость, разблокировать детей.
7. Провал: retry по политике gate; если всё равно провал — узел `failed`, дети `blocked`, Steward решает.
8. Стоп: все узлы терминальны, abort, бюджет или D4.

### 8.4. Resume

- Состояние каждого узла хранится в `run.json` по `id`, а не по индексу.
- `succeeded` пропускается; `failed`/`interrupted` повторяется; `blocked` ждёт решения.
- Если план изменился с момента чекпоинта, `--resume` отказывает: нужен `--from-plan` с явным подтверждением.
- Артефакты: `step-<id>.md`, `step-<id>-attempt-N.md`; индексные имена уходят.

### 8.5. Стоимость

- Стоимость считается по узлу.
- Лимит проверяется между волнами, а не внутри узла.
- Неизвестная цена + `max_cost` = отказ до старта.
- Итог печатает `cost=$X` или `cost=unknown`, без нулей вместо неизвестности.

### 8.6. Чего не делать

- Не делать универсальный DAG, где параллельные change-узлы правят один worktree.
- Не позволять планировщику добавлять агентов, права или permission-правила.
- Не делать неограниченный fan-out: 20 параллельных сессий — это счёт и rate limit, а не скорость.
- Не скрывать зависимости по файлам: если две задачи трогают один файл, они должны быть последовательны или разделены интерфейсным milestone.
- Не считать план источником истины. Источник истины — контракт + доска + evidence.

## 9. Масштаб: часы, десятки, сотни

| Горизонт | Единица работы | Состояние | Человеческие checkpoint-ы | Бюджет | Главный риск |
|---|---|---|---|---|---|
| **1–8 ч** | один прогон, 1 миссия, 3–8 задач | `run.json` + worktree | после контракта, перед merge | до $5 | неверное допущение |
| **10–40 ч** | 2–5 волн/дней, доска, 10–40 задач | доска + миссия + worktree | recon, options, границы milestone, 50/80% | $10–50 | context rot, устаревший план, дрейф merge |
| **100+ ч** | долгоживущая команда, 5–10 milestone, 50–200 задач | доска + миссия + ADR-лог + evidence store | недельный steering, milestone gates, 50/80%, D3/D4 | $100+ | неверная цель, накопленный дрейф, смена модели, дрейф репозитория |

### 9.1. 1–8 часов

- Один процесс, один worktree, `--resume` на случай падения.
- Человек утверждает контракт и смотрит финальный diff.
- План может быть плоским: 3–8 шагов.
- DAG не обязателен; параллельный recon уже даёт выигрыш.

### 9.2. 10–40 часов

- Процесс будет перезапускаться. Источник истины — доска, а не сессия.
- Свежая сессия на задачу; никакой «памяти агента» между волнами, только артефакты.
- 2–3 milestone; re-plan на границе milestone, а не каждый час.
- Ежедневная сводка: что сделано, что в review, что blocked, сколько потрачено.
- Worktree и ветки прошлых попыток не удаляются автоматически; нужен `--prune`.
- Baseline пересчитывается, когда основная ветка уехала.
- Человек смотрит не каждый diff, а milestone-границы и D3.

### 9.3. 100+ часов

- **Это не один прогон.** Это 20–50 волн по 2–6 часов с durable state между ними.
- Миссия переживает смену модели, перезапуск процесса и неделю дрейфа репозитория.
- Контракт версионируется; ADR-лог хранит, почему решение менялось.
- Появляется «mission control»: статус milestone, burn rate, blocked, drift-лог, ближайшие checkpoint-ы.
- Человек — не ревьюер каждого шага, а steering committee: недельный обзор, milestone acceptance, D3/D4.
- Нужен retention: ADR и mission хранятся долго; терминальные run-артефакты чистятся по сроку.
- Нужна защита от context rot: никаких 100-часовых сессий; каждая задача — свежая сессия с коротким контекстом.
- Нужна защита от «тихого расширения»: 80% бюджета — стоп на новый скоуп.
- Нужна защита от устаревших веток: worktree создаётся от текущего HEAD волны, старые ветки не мержатся без post-gate.

### 9.4. Что растёт нелинейно

- **Неопределённость.** Чем длиннее задача, тем дороже поздняя ошибка. Поэтому recon и options — не роскошь, а страховка.
- **Контекст.** Один агент не удержит 100 часов истории. Держат артефакты, а не чат.
- **Координация.** Параллельные писатели требуют интерфейсов; интерфейсы требуют отдельного шага.
- **Доказательства.** Чем дольше миссия, тем больше нужно evidence, но тем меньше человек хочет читать. Нужны сводки и фильтры.
- **Цена отката.** Чем позже найдена ошибка, тем дороже. Поэтому D3-checkpoint дешевле, чем D4-разбор.

## 10. Дорожная карта

Порядок: сначала снять ложные таймауты, потом закрепить контракт, потом включить read-only параллелизм, потом DAG на доске, потом Steward, потом длинный режим. Параллельные change-задачи — в конце: доска уже умеет их изолировать, но контракт и drift-контроль должны быть раньше.

| # | Кирпич | Что даёт | Оценка | Зависит от |
|---|---|---|---|---|
| 0 | Runtime P1 | async gate, `AbortSignal` на HTTP, честный cost cap | 2–4 дня | — |
| 1 | Mission contract v1 | верхний якорь: goal, non-goals, инварианты, acceptance, допущения, D1–D4 | 2–3 дня | — |
| 2 | Parallel analyze DAG | recon/options fan-out + join, без правок | 2–3 дня | 0, 1 |
| 3 | Hierarchical plan + board DAG | milestone → tasks, deps, одна цепочка в прогоне, пагинация | 4–6 дней | 1, 2 |
| 4 | Steward + drift-лог | `continue`/`rework`/`replan`/`escalate`, D1–D4, checkpoint-ы | 3–5 дней | 1, 2 |
| 5 | Long-horizon ops | prune, retention, mission control, ежедневные сводки | 3–5 дней | 3, 4 |
| 6 | Parallel change via board | 3+ change-задачи параллельно, serial merge, post-gate | 5+ дней | 0, 3, 4 |

### 10.1. Кирпич 0. Runtime P1

**DoD:**

- медленный check (10 с) + две параллельные задачи: ни одна не получает ложный `step timed out`;
- фейковый клиент, который не отвечает: шаг завершается по таймауту, процесс не висит, lock снимается;
- неизвестная модель + `--max-cost` = отказ; известная цена перекрывает таблицу;
- `npm run typecheck` и `npm test` зелёные.

**Риск:** async-рефакторинг протягивается через `pipeline.ts`, `apply.ts`, `team.ts`; легко пропустить один вызов.

### 10.2. Кирпич 1. Mission contract v1

**DoD:**

- `mission.json` валидируется: обязательные поля, acceptance с evidence, assumption-статусы;
- `--mission <path>` или `deus.json.mission` подхватывает контракт;
- `run.json` хранит `{ id, version, hash }`;
- планировщик видит goal, non-goals, инварианты и acceptance;
- `load_bearing + unverified` блокирует первый change-шаг;
- изменение контракта в середине прогона требует нового approval;
- контракт не может расширить права агента.

**Риск:** контракт разрастётся до документа на 10 страниц. Лечение: лимит на размер и шаблон.

### 10.3. Кирпич 2. Parallel analyze DAG

**DoD:**

- `PlanNode.dependsOn` и join-узел;
- 3 параллельные recon-ветки + synthesis завершаются без ложных таймаутов;
- change-узлы в pipeline-слое не параллельны;
- resume пропускает succeeded и повторяет interrupted;
- стоимость и артефакты считаются по узлу;
- невалидный граф падает до первой сессии.

**Риск:** частичный провал ветки. Пока нет Steward, политика fail-closed: ветка failed, дети blocked, человеку отчёт.

### 10.4. Кирпич 3. Hierarchical plan + board DAG

**DoD:**

- план миссии: 3–7 milestone, каждый с 5–20 задачами;
- задачи создаются на доске с `depends_on`, acceptance, workspace и бюджетом;
- один `--team-run` доводит цепочку `A → B → C`, если хватает раундов и бюджета;
- `waiting` считает всех, кто ждёт, включая >1000;
- задача не берётся раньше родителей;
- merge сериализован, post-gate обязателен.

**Риск:** сложность планировщика и доски. Лечение: milestone-границы, лимиты на размер, пагинация.

### 10.5. Кирпич 4. Steward + drift-лог

**DoD:**

- D1/D2 продолжаются и пишутся в `drift.md`;
- D3 останавливает ветку, готовит эскалационный пакет;
- D4 останавливает миссию;
- невалидный ответ Steward → `escalate`;
- `replan` сохраняет acceptance и не трогает контракт;
- 50/80/100% бюджета срабатывают;
- человек может восстановить причину каждого D2+ из артефактов.

**Риск:** ложные эскалации и дорогой советник. Лечение: короткий промпт, лимит стоимости, пилот на 10–40 часах.

### 10.6. Кирпич 5. Long-horizon ops

**DoD:**

- `--prune` чистит старые worktree/ветки/сессии по сроку;
- retention для run-артефактов; ADR и mission не чистяются;
- ежедневная сводка: milestone, burn rate, blocked, drift;
- mission control: список миссий, статус, бюджет, ближайший checkpoint;
- миграции БД с backup и `user_version` в транзакции.

### 10.7. Кирпич 6. Parallel change via board

**DoD:**

- 3 независимые change-задачи идут параллельно в разных worktree;
- merge и post-gate сериализованы;
- file-overlap детектится до старта (или задачи разводятся по milestone);
- ветка неудачной попытки остаётся видимой;
- контракт не меняется от merge.

**Риск:** семантические конфликты, которые git не видит. Лечение: интерфейсный milestone до параллельных change-задач.

## 11. Антипаттерны

| Плохо | Почему | Как надо |
|---|---|---|
| Закрепить архитектуру как верхний уровень | До recon она гипотеза; первый факт её ломает | Закрепить контракт, архитектуру сделать ADR |
| План как закон | Ломается от нового факта; агент либо тупо следует, либо молча отклоняется | План одноразовый, контракт постоянный |
| Универсальный DAG с параллельными change в одном worktree | Конфликты и потерянные правки | Pipeline DAG только read-only; change — через доску |
| Контракт на 10 страниц | Никто не читает, агент тоже | Один экран + JSON |
| Перечислить все отклонения заранее | Список неполный, новые случаи не покрыты | Классы D1–D4 + policy |
| Автоматически принимать D3 | Человек узнаёт о решении постфактум | D3 — checkpoint, D4 — стоп |
| Steward с инструментами | Он начнёт действовать без ревью | Steward — советник без инструментов |
| Мерить прогресс токенами/шагами | Активность не равна результату | Мерить acceptance evidence |
| Одна сессия на 100 часов | Context rot, деградация качества | Свежая сессия на задачу, артефакты вместо памяти |
| Верить памяти агента | Сессия умрёт, память исчезнет | Источник истины — доска, mission, ADR |
| «Готово» без gate | Это мнение, а не результат | `done` только после gate + review |
| Молчаливое превышение бюджета | Человек узнаёт, когда уже поздно | 50/80/100% checkpoint-ы |

## 12. Открытые вопросы

1. **Где живёт миссия?** Предложение: артефакт `.deus/missions/<id>/`; команда ссылается на одну активную миссию; прогон — на версию и хеш. Альтернатива: mission внутри `teams`-таблицы. Решение до кирпича 1.
2. **Кто утверждает изменение контракта в середине?** Предложение: только человек; раннер ставит на паузу. Автоматического approve нет.
3. **Как детектить семантический дрейф, а не только поверхностный?** Предложение: классификация по затронутым surface + новые зависимости + изменения acceptance; семантику смотрит Steward и человек на milestone. Это ГИПОТЕЗА, нужен пилот.
4. **Сколько checkpoint-ов на 100 часах?** Предложение: контракт, recon, options, каждый milestone, 50/80%, D3/D4. Проверить на пилоте 10–40 часов.
5. **Нужен ли отдельный агент-архитектор для options?** Предложение: использовать существующих `architect-planner` и `reviewer-critic` с разными линзами; отдельную роль вводить только если качество вариантов будет низким.
6. **Где хранить evidence для 100 часов?** Предложение: `.deus/missions/<id>/` + `runs/` + board DB; retention: ADR и mission навсегда, run-артефакты — по сроку.
7. **Как поступать с дрейфом основной ветки?** Предложение: worktree от текущего HEAD волны; re-baseline; старые ветки не мержить без post-gate.
8. **Что делать, если человек недоступен?** Предложение: D3 ждёт до deadline; после — ветка `blocked`, независимые ветки продолжаются; автоматического разрешения нет.
9. **Как не дать планировщику переразбить задачу?** Предложение: 3–7 milestone, 5–20 задач на milestone; больше — дробить миссию.
10. **Нужен ли KB из V1 для длинных миссий?** Предложение: пока нет; ADR-лог и recon-артефакты дешевле и точнее. Вернуться, если поиск по решениям станет узким местом.

## 13. Критерии приёмки дизайна

Дизайн считается рабочим, если:

1. 10-часовая миссия проходит с двумя человеческими checkpoint-ами (контракт и финальный merge) и даёт evidence по каждому пункту acceptance.
2. 100-часовая миссия переживает перезапуск процесса, смену модели и неделю дрейфа репозитория; ни одна задача не становится `done` без gate; каждое отклонение D2+ есть в drift-логе.
3. Load-bearing допущение со статусом `unverified` останавливает первый change-шаг, а не всплывает через 20 часов.
4. Три параллельные read-only ветки завершаются без ложных таймаутов; три параллельные change-задачи мержатся последовательно с post-gate.
5. `max_cost` останавливает миссию на пороге; неизвестная цена + `max_cost` = отказ до старта.
6. Планировщик не может добавить агента, право или изменить контракт.
7. Человек может восстановить причину каждого решения из артефактов: mission, ADR, drift, run.json, board events.
8. После D3-паузы независимые ветки продолжаются, а не встаёт вся миссия.
9. Ретро даёт хотя бы один новый инвариант или автоматизированную проверку, а не только текст.

## 14. Не-цели

- Это не песочница и не граница безопасности. Изоляция процесса (контейнер/uid) остаётся единственным настоящим путём.
- Это не замена продуктовым решениям человека. Агент не выбирает цель и не меняет критерии успеха.
- Это не универсальный workflow для любой задачи. Для задачи на 20 минут хватит `--direct`.
- Это не multi-tenant сервис и не облачная платформа.
- Это не гарантия правильного кода. Это гарантия того, что результат проверен и отклонения видны.
- Это не обещание нулевого участия человека. Обещание — редкие и осмысленные checkpoint-ы.

## 15. Глоссарий

| Термин | Значение |
|---|---|
| **Миссия** | Одна долгая задача с целью, контрактом и бюджетом |
| **Контракт** | Машинный `mission.json`: goal, non-goals, инварианты, acceptance, допущения, права |
| **Инвариант** | Условие, которое должно оставаться истинным всегда |
| **Acceptance** | Проверяемый пункт «готово» с evidence |
| **Допущение** | Утверждение, которое может быть неверным; имеет статус и `load_bearing` |
| **D1–D4** | Классы отклонений: локальная реализация, локальный дизайн, кросс-граница, контракт |
| **Steward** | Советник без инструментов, применяющий коридор отклонений |
| **Milestone** | Крупная граница миссии с собственным acceptance и бюджетом |
| **Task** | Единица доски с зависимостями и workspace |
| **Wave** | Один прогон ready-set задач |
| **Board** | SQLite-доска задач с CAS-арендой и событиями |
| **Gate** | Проверки проекта + baseline + сравнение падений |
| **Worktree** | Отдельное git-дерево для изоляции прогона или задачи |
| **ADR** | Architecture Decision Record: что решили, почему, что отвергли |
| **Drift-лог** | Запись отклонений D2+ с причиной, ценой и последствиями |

## 17. Решение, которое нужно принять

До начала кода нужно ответить на один вопрос:

> **Строим контракт миссии первым или сначала чиним runtime?**

Рекомендация: **runtime P1 (кирпич 0) первым**, потому что он короткий и снимает ложные таймауты, на которых уже сейчас спотыкается `--team-parallel 3`. Сразу за ним — контракт (кирпич 1), потому что он задаёт acceptance для всего остального. Дальше read-only DAG, доска, Steward, длинный режим.

Если хочется быстрый видимый результат — можно сделать кирпич 2 (parallel analyze) сразу после 0, не дожидаясь полного контракта. Но тогда acceptance придётся задавать вручную в задаче, а не в миссии; это временный режим, не целевой.

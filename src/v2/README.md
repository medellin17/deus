# Deus V2 runner

Детерминированный раннер автономных прогонов поверх OpenCode 2.x.

Он не поднимает свой сервер и не использует V1 SDK. Раннер подключается к общему
OpenCode-сервису через `@opencode/client`, создаёт отдельную сессию на каждый шаг,
сам отвечает на permission-запросы, проверяет результат командами проекта и
сохраняет чекпоинт после каждого шага.

## Требования

- OpenCode 2.x с запущенным сервисом (`opencode` уже работает; `Service.discover()` найдёт его).
- Node.js 20+ (проверено на Node 26).
- Git-репозиторий в целевом проекте (для изоляции в worktree; можно отключить `--no-worktree`).

## Быстрый старт

```bash
npm install
npm run v2:smoke
```

`smoke` проверяет связку «сервис → модель → сессия → ответ» без изменения проекта.

Прогон:

```bash
npm run v2 -- --cwd /path/to/project --pipeline build "Добавь multiply(a, b) в math.js и тест"
```

## Настройки проекта: `deus.json`

Файл лежит в корне проекта и читается автоматически. Флаги командной строки
перекрывают значения из файла.

```json
{
  "model": "opencode-go/hy4-flash-free#high",
  "timeoutSeconds": 900,
  "maxCost": 0.2,
  "pipeline": "build",
  "worktree": true,
  "merge": true,
  "baseline": true,
  "policy": ".deus/policy.json",
  "checks": {
    "test": "npm test",
    "typecheck": "npm run typecheck"
  }
}
```

Все поля необязательны. `checks` — именованные команды проверки; массив команд
склеивается через `&&`. Если `checks` нет, раннер ищет `test` в `package.json`.
Файл конфига должен быть закоммичен: `.deus/` целиком в `.gitignore`.

## Пайплайны

| Пайплайн | Шаги | Когда |
|---|---|---|
| `build` | `plan` → `implement` → `review` | Новая фича или изменение |
| `fix` | `investigate` → `fix` → `verify` | Баг с неизвестной причиной |
| `audit` | `survey` → `audit` → `synthesize` | Аудит без изменений в коде |
| `auto` | план от LLM-планировщика | Нестандартная задача |

`plan`, `investigate`, `survey`, `review`, `verify`, `audit`, `synthesize` работают
с запретом на `edit`, `shell` и `subagent`. Реализация (`implement`, `fix`) получает
полный доступ, но её действия ограничены permission-политикой и worktree.

## Планировщик

```bash
npm run v2 -- --cwd /path/to/project --pipeline auto "Перепиши загрузчик конфигов на новый формат"
```

Планировщик — отдельный шаг с агентом `plan`. Он возвращает JSON:

```json
{
  "goal": "переписать загрузчик",
  "steps": [
    { "id": "investigate", "agent": "plan", "mode": "analyze", "task": "найди текущий загрузчик" },
    { "id": "rewrite", "agent": "build", "mode": "change", "task": "перепиши загрузчик" },
    { "id": "review", "agent": "build", "mode": "analyze", "task": "проверь diff" }
  ]
}
```

Ограничения плана:

- 1–8 шагов, уникальные `id`;
- агент только из списка существующих агентов OpenCode;
- `analyze` — только чтение, `change` — правки и команды;
- если есть `change`, последний шаг обязан быть `analyze`;
- свои permission-правила и новых агентов план создать не может.

Посмотреть план без запуска:

```bash
npm run v2 -- --cwd /path/to/project --plan-only "та же задача"
```

План сохраняется в `.deus/runs/<runId>/plan.json` и печатается в stdout. Его можно
поправить руками и запустить (задачу можно не повторять — возьмётся `goal` из плана):

```bash
npm run v2 -- --cwd /path/to/project --from-plan plan.json
```

Невалидный ответ планировщика повторяется дважды с текстом ошибки. После этого
прогон падает, а не подменяется фиксированным пайплайном.

## Проверка результата (gate)

Шаги реализации (`implement`, `fix` и все `change`-шаги плана) помечены `gate`.
Если такой шаг не изменил ни одного файла, он падает с `step produced no changes`:
для change-задачи пустой diff — это не успех.
После шага раннер сам запускает команды проверки из `deus.json` (или
`npm test`, если конфига нет):

- exit code 0 — шаг принят;
- ошибка — раннер запускает шаг ещё раз, приложив вывод упавшей команды;
- по умолчанию две попытки всего, затем прогон падает.

Перед первым gated-шагом раннер один раз запускает проверки на нетронутом worktree —
это baseline. Дальше результаты сравниваются:

- baseline зелёный — любая ошибка блокирует шаг;
- baseline красный, падают те же тесты — шаг проходит с предупреждением;
- появились новые падающие тесты — шаг падает и уходит в retry.

Сравнение идёт по именам упавших тестов в выводе (node:test, jest, mocha, vitest,
pytest, go test). Компиляторные и тулзовые ошибки (`error TS…`, `error[E…]`,
`error:`, `make: *** … Error N`, `ENOENT`, `sh: N:`, `panic:`, `Segmentation fault`,
`Killed`) сравниваются построчно и не прячутся за уже известным падением.
Runtime-ошибки (`AssertionError`, `TypeError`, …) сравниваются по классу: изменившийся
текст ассерта — не новое падение, новый класс ошибки — падение. Любой timeout
считается провалом: прогон, который не успел провериться, не мержится.
Если baseline был красным, запускаются все проверки, а не только первая. Если
текущий вывод не распознан: идентичный вывод считается pre-existing, изменившийся —
падением (сравнить нельзя, поэтому fail-closed). Отключить сравнение:
`--no-baseline` или `"baseline": false`.

Вывод проверок сохраняется в артефакт шага, baseline — в `run.json`.
Отключить проверки совсем: `--no-gate`.

Чего gate не делает:

- не мешает агенту удалить тест полностью — в промпте есть запрет, а review-шаг
  видит diff, но машинной гарантии нет;
- не устанавливает зависимости. В worktree `node_modules` симлинкуется из проекта,
  если git его игнорирует; иначе проверки могут не запуститься;
- не гарантирует распознавание новых падений в нестандартном формате вывода.

## Результат в основном дереве

После успешного прогона worktree коммитится в ветку `deus/<runId>`.

Авто-мерж выполняется, если:

- прогон завершился успешно;
- основное дерево чистое;
- проект не в detached HEAD.

`HEAD` может сдвинуться за время прогона. Если слияние проходит без конфликтов —
оно выполняется сразу. Если есть конфликты, раннер запускает агента `build` в
основном дереве: агент правит только конфликтные файлы, без shell и без коммита.
Технически edit разрешён только на файлы из списка конфликтов; `.git`, `.deus`,
`node_modules`, секреты, webfetch и внешние пути запрещены.
После агента раннер проверяет, что не осталось маркеров и правок вне списка,
прогоняет checks и делает merge-коммит. Если checks создали файлы вне конфликтов,
авто-мерж отклоняется. Любой сбой — `git merge --abort`, изменения остаются в ветке.

Перед мержем проверяется, что проект на той же ветке, что и при старте, история
содержит базовый коммит, дерево чистое, а ветка не трогает untracked-файлы под
ignore-правилами. Иначе раннер не трогает основное дерево и оставляет ветку.
Пустая ветка (коммит не состоялся) не считается влитой: раннер до-коммитит
изменения, а если worktree чист — возвращает `skipped`.

Мерж идёт через `--no-ff`, поэтому весь прогон откатывается одним `git revert -m 1`.
Если авто-мерж выключен или условия не выполнены, раннер оставляет ветку и
печатает команду мержа. Отключить авто-мерж: `--no-merge`.

Код выхода: `0` — успех и мерж выполнен (или изменений нет), `1` — прогон упал,
`2` — прогон успешен, но изменения остались в ветке и требуют ручного мержа.

```bash
npm run v2 -- ...              # авто-мерж при чистых условиях
npm run v2 -- --no-merge ...   # только ветка
```

## Один агент

```bash
npm run v2 -- --cwd /path/to/project --direct --agent build "Почини тест в math.test.js"
```

`--direct` не запускает пайплайн: один шаг, один агент. Результат проверяется
gate, как обычный шаг; отключить: `--no-gate`.

## Таймауты и зависший провайдер

`--timeout` (секунды, по умолчанию 900) — предел на шаг. Дополнительно работает
watchdog на «нет первого вывода»: если за 5 минут (`firstOutputMs`) сессия не отдала
ни одного токена, раннер прерывает её и падает с сообщением
`no model output after 300s: the provider did not start responding` вместо
молчаливого ожидания всего таймаута. Так выглядит зависший провайдер: сессия
«busy» без токенов, а `npm run v2:smoke` тоже отвечает таймаутом.

Watchdog закрывает именно отсутствие первого ответа. Если зависание случилось
посередине шага (токены уже пошли), сработает общий `--timeout`.

## Resume

Если процесс убит или получил `Ctrl+C`, раннер прерывает активную сессию и пишет
чекпоинт. Продолжить:

```bash
npm run v2 -- --cwd /path/to/project --resume run-20261121T114203
```

Успешные шаги не повторяются. Повторяется только шаг, который был прерван или упал.
Если шаг упал на проверках, при возобновлении в промпт попадает вывод проверок.
Worktree и план берутся из чекпоинта. Модель прогона — фолбэк: `model` из шапки агента
применяется и на возобновлении, явный `--model` перекрывает всё.

## Worktree

По умолчанию прогон идёт в отдельном git worktree:

```
<project>/.deus/worktrees/<runId>
```

Это защищает основное дерево от изменений агента. Незакоммиченные изменения в
основное дерево **не попадают** — worktree создаётся от `HEAD`. Если нужен прямой
прогон:

```bash
npm run v2 -- --no-worktree ...
```

`node_modules` из проекта симлинкуется в worktree, если он есть и git его игнорирует:
без этого проверки не найдут зависимости. `--cwd` должен указывать на корень
git-репозитория; подкаталог (monorepo package) отклоняется с понятной ошибкой.

После прогона worktree остаётся для ревью. Изменения уже закоммичены в ветку,
поэтому смотреть их нужно из основного дерева:

```bash
git -C <project> diff <baseCommit>..deus/<runId>
```

`<baseCommit>` есть в `run.json`.

Удалить worktree после успеха: `--cleanup`. Удаление пропускается, если изменения
не удалось закоммитить.

## Permission-политика

По умолчанию раннер разрешает обычные команды и запрещает опасные:

- `git push` (в том числе `git -C … push`)
- `git reset --hard`
- `git clean -f`
- `rm -rf /` (в том числе `rm -rf -- /`)
- `sudo`
- `mkfs`, `dd if=`
- `shutdown`, `reboot`
- `curl | sh`, `wget | bash`
- чтение и правка `.env`, `*.env`, `.envrc`, приватных ключей (`*.pem`, `*.key`, `*.p12`, `*.pfx`) и `.ssh/.aws/.gnupg`
- `env`, `set`, `printenv` через shell
- `webfetch`, `websearch`, `external_directory`

Свой файл: `.deus/policy.json` в проекте, `policy` в `deus.json` или `--policy <file>`.

```json
{
  "default": "allow",
  "rules": [
    { "match": "git push", "decision": "deny", "reason": "push is a human decision" },
    { "match": "npm test", "decision": "allow", "reason": "tests are safe" }
  ]
}
```

Правила применяются по порядку, побеждает последнее совпадение. `match` — регулярное
выражение по строке `action resource`. `deny` отправляется агенту как `reject`,
`allow` — как `once`.

Раннер принудительно переводит `shell` в `ask` на уровне сессии и отвечает сам,
поэтому политика применяется и к агентам, у которых shell разрешён по умолчанию.
То же для чтения `.env`, ключей, `.ssh/.aws/.gnupg` и `webfetch`: они приходят как
`ask` и решаются политикой. `deny` из policy-файла имеет приоритет над разрешениями
агента. Плата за это — до ~250 мс на shell-команду, пока раннер отвечает на запрос.

Широкое правило вида `{"match":".*","decision":"allow"}` перекрывает встроенные
запреты: policy-файл доверенный, но это стоит помнить.

### Это не песочница

Политика — набор предохранителей, а не граница изоляции. Проверено чтением кода и
живыми пробами:

- Правила матчатся по строке `action resource`, то есть по сырому тексту команды, а
  не по разобранному argv. Обход через `xargs`, `base64 -d | sh` или «записать
  скрипт, потом запустить» не ловится.
- `defaultDecision` по умолчанию `allow`: действие, которого нет среди deny-правил
  (нестандартный MCP-тул, новый tool), будет разрешено.
- Набор действий задаёт сервер: правило `read <path>` сработает, только если агент
  шлёт именно `read`. Для абсолютного пути вне проекта сервер обычно шлёт
  `external_directory`, и тогда срабатывает deny-правило — но это поведение
  сервера, а не гарантия раннера.
- `shell` приходит как `ask` и решается по тексту команды, поэтому `bash -c '...'`,
  `node -e '...'` и подобные проходят ту же текстовую проверку, а не разбор
  аргументов.

Реальная изоляция (чужие креды, сеть, файловая система хоста) — задача sandbox'а или
контейнера вокруг процесса. Политика нужна, чтобы агент не сделал глупость по
ошибке, а не чтобы остановить того, кто сознательно ищет обход.

## Реестр агентов

Раннер читает шапку (frontmatter) `.opencode/agents/*.md` из рабочей директории прогона.
Кроме нативных полей OpenCode (`model`, `tools`, `permission`, `temperature`, `steps`)
понимает четыре своих:

| Поле | Значение | По умолчанию |
|---|---|---|
| `role` | метка роли для доски и планировщика | `worker` |
| `reports_to` | id агента, которому подчиняется (≤ 2 уровней, без циклов) | — |
| `workspace` | `read-only` или путь внутри проекта | без сужения |
| `budget` | `{ maxCost, maxSteps }` | — |

Все четыре необязательны. Битое поле, незакрытый блок или битый YAML — падение до первой
сессии, с именем файла.

**Что уже действует:** `model` из шапки — раннер берёт его для шага, если не задан явный
`--model` (явный флаг старше шапки, шапка старше `deus.json`); это работает и на `--resume`.

**Что пока только данные:** `role`, `reports_to`, `workspace`, `budget` читаются и
валидируются, но прогон ещё не ограничивают — их потребители появятся в следующих кирпичах.
`tools` — нативное поле: его соблюдает сам сервер OpenCode по тому же файлу, раннер лишь
проверяет форму.

Сервер OpenCode лишние ключи в шапке принимает (проверено живым прогоном), но `agent.list`
их не отдаёт, поэтому реестр читает файлы сам.

## Доска задач

Долгоживущая команда ведёт задачи в `<project>/.deus/board.db` (SQLite, WAL).
`--board` открывает базу **только на чтение**: ничего не создаёт и не меняет.

Статусы: `backlog → claimed → running → review → done`, плюс `blocked` и `cancelled`.
`running → done` запрещён: результат обязан пройти `review`, а в `done` задачу переводит
только пройденный gate (`verification.status = passed`). Доска сама проверки не запускает:
вызывающий передаёт результат `gate.ts` в `submit`, и только он отвечает за его правдивость.

Задачу забирает один: аренда идёт через CAS, `claimed` живёт по лизингу от 1 до 600 с
(по умолчанию 120), просроченную аренду можно перехватить. У `running` лизинга нет: если
исполнитель умер и токен потерян, задачу возвращает ведущий команды (`block`, затем
`retry`) — без токена это разрешено только ему. Зависимости (`depends_on`) не дают взять
задачу раньше предков. Каждый переход пишет событие в той же транзакции, а write-транзакции
берут блокировку сразу (`BEGIN IMMEDIATE`), иначе несколько процессов ловят
`SQLITE_BUSY_SNAPSHOT`.

Уборка не автоматическая: `prune()` (по умолчанию `done`/`cancelled` — 30 дней, события —
90) вызывается явно. Задачи, от которых зависят живые, не удаляются; события живых задач
сохраняются, чистится только висячее.

Имя команды уникально среди **активных**. После `closeTeam` имя освобождается, и при
следующем открытии создаётся новый активный `main`.

### Доска из CLI

Читать — `--board`. Менять — `--board-task <действие>` с `--board-id`; актор по умолчанию
`main` (`--board-actor`), а `assignee` при создании задаётся отдельно (`--board-assignee`).
Вывод машинно-читаемый: `add` печатает `task: <id>`, остальные действия — `task: <id> status: <…>`,
`claim` — `claim_token:` и `lease_until:`. Проигранная гонка за задачу — не ошибка:
строка начинается с `claim: none`, exit 0.

```bash
deus --team-add --team-name research --team-goal "…"
deus --board-task add --board-title "…" --board-goal "…" [--board-team main]
deus --board-task claim --board-id bt-…
deus --board-task start --board-id bt-… --board-token … --board-execution-ref run-…/step
deus --board-task submit --board-id bt-… --board-token … --board-gate passed --board-summary "…"
deus --board-task accept --board-id bt-…
deus --board-task rework --board-id bt-… --board-note "что поправить"
deus --board-task retry --board-id bt-…
deus --board-task block --board-id bt-… --board-reason "…" [--board-token …]
deus --board-task cancel --board-id bt-… [--board-token …]
```

`submit` требует явный `--board-gate`: доска не угадывает, прошли проверки или нет.
Ошибка печатается как `error: <код>: <текст>` и даёт exit 1. Код есть у переходов доски
(`invalid_transition`, `not_owner`, `verification_required`, `not_found`…) и у ошибок
аргументов (`invalid_input`), так что агент-ведущий разбирает код, а не строку.

## Команда: worktree, gate, merge

Кодинговая команда — это конвейер, а не чат: каждый агент пишет в своё дерево, а `done` на
доске означает «изменения влиты и проверены».

```bash
deus --team-add --team-name coding --team-goal "…"
deus --board-task add --board-title "…" --board-goal "…" --board-team coding
deus --team-run --team-name coding --team-parallel 3
```

Ход одной задачи:

1. `claim` — один писатель на задачу (CAS на доске);
2. worktree `.deus/worktrees/t-<taskId>-a<attempt>-<run>`, ветка `deus/t-<taskId>-a<attempt>-<run>` —
   в имени и попытка, и прогон, поэтому ни повтор после `rework`, ни перезапуск после сбоя не
   упираются в старое дерево;
3. агент работает в этом дереве, сессия шага пишется в `run.json` (по ней `rework` найдёт
   исполнителя);
4. проверки проекта (`checks` из `deus.json`) идут **до** коммита, с сравнением baseline;
5. ветка коммитится и вливается в проект по одной (merge сериализован);
6. проект проверяется ещё раз **после** merge — в одноразовом дереве от нового HEAD;
7. `submit` + `accept` идут подряд в одном процессе: сам раннер окна «принять невлитое»
   не оставляет. Отдельная волна `--wake`, идущая параллельно, может успеть забрать событие
   до `accept` и разбудить лида по уже закрытой задаче — это шум, а не порча: `accept`
   отменит только ещё не забранное событие.

Без проверок команда не работает: `--no-gate` отвергается как `invalid_input`, пустой
`checks` — как `no_checks`. Это намеренно: `accept` требует `verification.status="passed"`, а
ключом к нему может быть только настоящий gate.

| Исход | Что происходит |
|---|---|
| gate упал | `submit(failed)` + комментарий, задача в `review`, `accept` откажет |
| коммит не удался | `block(reason)`, задача в `blocked`, лид получает пробуждение |
| merge конфликтует | `submit(failed)` + комментарий с именем ветки, задача в `review` |
| post-merge gate упал или упал сам процесс проверки | merge откатывается к коммиту, который был до него, задача в `blocked`; если слияние было уже сделано раньше, проект не трогается; если откат не удался, это написано в причине |
| агент не ответил | `block(reason)`, коммита нет |

Exit-коды: `0` — все задачи `done` (или брать было нечего); `2` — есть `review`/`blocked` или
прогон прерван (`skipped: interrupted`), то есть человеку есть что решать; `1` — ошибка
прогона (не git, грязный проект, нет проверок, занято). Прогон требует чистого проекта
(`error: dirty_worktree`) и один на проект (`.deus/team.lock`, `error: team_busy`). Если lock
остался от чужого процесса, который уже мёртв, раннер снимет его сам; если pid переиспользован
другим процессом, файл придётся удалить руками.

Что делать с `review`: `--board-task rework --board-id … --board-note "…"` вернёт задачу в
работу и разбудит исполнителя; `--board-task cancel` закрывает её. `blocked` лечится
`--board-task retry` (или `cancel`). Стоимость прогона печатается в итоговой строке.

Флаги, меняющие смысл прогона (`--no-merge`, `--max-cost`, `--json`, `--cleanup`, `--direct`,
`--pipeline`, `--worktree`, `--baseline`, `--no-gate`), вместе с `--team-run` отвергаются:
иначе они молча не действовали бы.

Границы: проверки в параллельных деревьях делят `node_modules` через симлинки — они должны
быть read-only; merge и post-gate сериализованы; ветки неудачных попыток остаются видимыми и
автоматически не удаляются; набор задач фиксируется на старте, поэтому цепочка зависимостей
`B depends A` доедет вторым прогоном; `--resume` на `run.json` команды отказывает явно;
проверки идут до коммита, поэтому файлы, которые проверка переписала (форматтер, снапшоты),
попадают в коммит вместе с работой агента; фильтр секретов — эвристика по именам файлов
(`.env*`, `*.pem`, ключи), а не гарантия.

## Пробуждения (wake)

Завершение задачи должно само доходить до того, кто обязан действовать. Outbox живёт в той
же `board.db` (`wake_events`), потому что событие и смена статуса обязаны коммититься одной
транзакцией: падение между ними не теряет пробуждение.

| Переход | Событие | Кто получает |
|---|---|---|
| `submit` (`running → review`) | `task/review-ready` | ведущий |
| `block` (`→ blocked`) | `task/blocked` | ведущий |
| `rework` (`review → backlog`) | `task/rework` | сессия исполнителя из `execution_ref` |
| `accept`/`retry`/`cancel` | — | никого не будят |

`accept`/`retry`/`rework`/`cancel` гасят ещё не доставленные события этой задачи (`cancelled`),
кроме той, что доставляется прямо сейчас: иначе ведущего разбудят по задаче, которая уже
закрыта. `rework` вместо этого будит сессию исполнителя и передаёт ей примечание ведущего;
если сессию по `execution_ref` найти не удалось, событие не создаётся. Если сессия
найдена, но уже удалена, событие пройдёт ретраи и станет `failed`, а примечание останется
в событии `task/reworked` на доске — до воркера оно не дойдёт.

Дедуп — уникальный `dedup_key` (`<event>:<task>:<attempt>`), он переживает рестарт.
Забрать событие может один: CAS по `pending` + аренда 60 с; просроченную аренду перехватывает
следующий проход, а событие, которое доставляется прямо сейчас, sweep не трогает. Событие
старше дедлайна (по умолчанию час) закрывается как `expired`, а не доставляется с опозданием.
Ошибка доставки даёт backoff (1, 2, 4, 8 мин) и после пяти попыток переводит событие в
`failed` с причиной; `failed` автоматически не оживает.

Адрес ведущего хранится в `.deus/team-lead-session.json`:

```bash
node --import tsx src/v2/cli.ts --wake-register <sessionID> --cwd <project>
```

Регистрация проверяет, что сессия читается, и работает даже при включённом kill-switch.
Если адреса ещё нет, событие **не сжигает попытки**: оно откладывается с причиной и остаётся
`pending`, а после регистрации подхватывается в начале следующей волны — ждать отложенного
повтора не нужно.

Доставка только ставит сообщение в очередь сессии (`wait: false`) — волна не блокируется на
ходе агента. **Жёсткие** потолки: число доставленных сообщений (склеенная пачка — одно
сообщение) и wall-clock. **Стоимость мягкая и считается по волне, а не по всей истории:**
при отправке пишется базовая стоимость сессии, `reconcileCosts` позже считает дельту, и
волна останавливается только по стоимости **своих** доставок. Поэтому накопленный за неделю
расход не блокирует очередь, а `--wake-max-cost 0` останавливает волну до первой доставки.
Стоимость склеенной пачки считается один раз, а не по числу событий. Если провайдер
заявляет `cost: 0` даже на платной модели, дельта токенов оценивается по модели сессии —
иначе бюджет был бы невидим.

События одному адресату в окне 30 с (в обе стороны) склеиваются в одно сообщение (до 10
задач), но каждая строка помечается `delivered`. Исчерпанный потолок даёт исход
`budget_exhausted` и оставляет остаток в `pending` — молчаливого вытеснения нет. `prune()`
чистит терминальные события вместе с задачами по тому же сроку.

Kill-switch: `.deus/wake.disabled` или `DEUS_WAKE=0`; проверяется перед каждой доставкой
(dry run ничего не доставляет).

```bash
node --import tsx src/v2/cli.ts --wake --cwd <project>          # одна волна
node --import tsx src/v2/cli.ts --wake-status --cwd <project>   # очередь, read-only
```

`--wake` не создаёт базу по опечатке в `--cwd`: если доски ещё нет, он просто сообщает об
этом. `--wake-status` на базе, созданной до появления outbox, пишет «outbox is not created
yet» вместо SQL-ошибки.

## Сообщения в сессию

Адрес сессии — её `sessionID`; он сохраняется в `run.json` для каждого шага, поэтому к
сессии можно вернуться после рестарта. `followUp` отправляет ещё один ход в существующую
сессию с явным `delivery: "queue"`: по умолчанию ждёт ответ, `wait: false` только ставит
сообщение в очередь.

Ответ ищется **после границы нашего user-сообщения** (его id возвращает `session.prompt`) и
**до начала следующего блока**: `user`, `synthetic`, `system`, `shell` или `compaction`.
Поэтому ни вывод текущего хода, ни `stop` следующего (в том числе синтетического) не
подставляются как наш ответ, а если наше сообщение так и не появилось — это таймаут, а не
чужой текст. Информационные сообщения вроде `idle` или `model-selected` ход не обрывают.

Сообщение в работающую сессию не вклинивается в генерацию: сервис выполняет его после
текущего хода. Это очередь, а не перехват. Если после admitted сообщения 60 с нет ни нового
assistant, ни роста токенов — `failed` («провайдер молчит или сообщение в очереди»).

Общий таймаут — 120 с. При таймауте или abort во время ожидания сообщение уже доставлено,
поэтому `delivered` остаётся `true`, а в ошибке сказано, что оно могло остаться в очереди;
авто-повтора нет. Если сигнал уже отменён **до** отправки, сообщение не отправляется вовсе.
Отмена во время ожидания не прерывает сам ход. Пустой текст отклоняется до отправки.
Ответ обрезанный провайдером (`finish: "length"`) считается ошибкой, а не успехом, но
частичный текст возвращается вместе с ошибкой. Стоимость хода — дельта от границы нашего
сообщения, поэтому расход предыдущего хода в неё не попадает; если прочитать метаданные на
границе не удалось, дельта считается от пред-отправочного снимка и может быть шире.

`messageTask` находит сессию задачи по `execution_ref` (`run-…/step-id` → `run.json`); при
нескольких шагах с одним id берётся **последний с непустым `sessionID`**, а id прогона
должен иметь вид `run-[A-Za-z0-9]+`. Если переданы `board` и `actor`, доставленное сообщение
пишется в `task/message` — даже когда ответа не дождались. Сбой записи в доску не теряет
ответ: он возвращается с `boardLogged: false` и причиной в `boardError` (поле `error`
остаётся только за провалом самого хода). Без `actor` событие не пишется, и это тоже видно
в `boardError`. Комментарии разрешены и в закрытой команде.

Модуль пока **библиотечный**: из CLI его никто не вызывает, первым потребителем будет wake
(кирпич 4). Стоимость follow-up возвращается вызывающему, но пока **не** пишется в
`run.json` и не входит в `--max-cost`; это подключится там же, иначе долгоживущая команда
обойдёт бюджет прогона.

## Ограничения текущего среза

- Планировщик недетерминирован: два запуска на одну задачу дадут разные планы.
- Нет параллельных шагов и DAG: шаги идут строго по очереди.
- Сравнение с baseline — эвристика: идентичный нераспознанный вывод считается pre-existing, изменившийся — падением. Нестандартный reporter может дать ложное падение, но не ложный зелёный. Timeout любого check — всегда провал. Fatal-сравнение построчное: изменившееся сообщение pre-existing ошибки считается новым fatal.
- Checks, создавшие неигнорируемые файлы вне конфликтов, блокируют авто-мерж — by design.
- Permission-запрос, на который reply не удался 5 раз, остаётся без ответа и ждёт step timeout.
- Если сессия исчезла до подсчёта, стоимость шага не подтягивается.
- `external_directory: deny` отрезает агенту и глобальные skills/config (`~/.agents`, `~/.config/opencode`).
- Если check делает `git add` вне конфликта, это не видно проверке и может попасть в merge-commit; отменённый merge оставляет untracked-файлы checks в проекте.
- Авто-abort незавершённого merge может отбросить ручные правки, если ты разрешал конфликты, но не коммитил.
- При timeout проверки убивается только shell, дочерние процессы (`npm test` в watch-режиме) могут остаться.
- Стоимость при жёстком падении процесса между шагами может быть недосчитана.
- untracked-файлы не показываются в diff для review (только имена в `git status`).
- Policy-файл с широким `{"match":".*","decision":"allow"}` ослабляет встроенные запреты.
- Секреты и `.env` в worktree не копируются: проверки, которым нужны реальные креды, могут не пройти.
- Разрешение конфликтов делает агент: при противоречивых намерениях он может выбрать неверную сторону. Checks обязательны, review лишь рекомендует — его вердикт не парсится.
- Resolver правит только конфликтные файлы; `.git`, `.deus`, `node_modules`, секреты и внешние пути запрещены. Checks, создавшие файлы вне конфликтов, блокируют авто-мерж.
- Permission-запросы дочерних subagent-сессий не опрашиваются: раннер отвечает только за корневую сессию.
- Ветка `deus/<runId>` после мержа остаётся; удалить: `git branch -d deus/<runId>`.
- KB/smart-context из старого deus не подключены к V2-раннеру.
- Сессии по умолчанию сохраняются для отладки. Их можно удалить через TUI/API.
- `--pipeline auto` берёт список агентов у сервера. Если для каталога он пуст, используется серверный дефолт; если пуст и он — run падает до планировщика (`no agents available for <dir>`). Планировщик видит только этот список, поэтому проектные агенты, которых сервер не отдал, ему недоступны.
- Коммит из worktree делает `git add -A`, но перед коммитом раннер отказывается от путей, похожих на секреты (`.env`, `.envrc`, `*.pem/key/p12/pfx`, `id_rsa`, `.ssh/.aws/.gnupg`): прогон завершается `refusing to commit secret-like files`, изменения остаются в worktree.

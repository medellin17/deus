# Deus V2 runner

Детерминированный раннер автономных прогонов поверх OpenCode 2.x.

Он не поднимает свой сервер и не использует V1 SDK. Раннер подключается к общему
OpenCode-сервису через `@opencode/client`, создаёт отдельную сессию на каждый шаг,
сам отвечает на permission-запросы, проверяет результат командами проекта и
сохраняет чекпоинт после каждого шага.

## Требования

- OpenCode 2.x с запущенным сервисом (`opencode` уже работает; `Service.discover()` найдёт его).
- Node.js 20+ (проверено на Node 26).
- Git-репозиторий в целевом проекте (для изоляции в worktree; можно отключить `--no-worktree`).

## Быстрый старт

```bash
npm install
npm run v2:smoke
```

`smoke` проверяет связку «сервис → модель → сессия → ответ» без изменения проекта.

Прогон:

```bash
npm run v2 -- --cwd /path/to/project --pipeline build "Добавь multiply(a, b) в math.js и тест"
```

## Настройки проекта: `deus.json`

Файл лежит в корне проекта и читается автоматически. Флаги командной строки
перекрывают значения из файла.

```json
{
  "model": "tokenharbor/deepseek-v4.1-flash:free",
  "timeoutSeconds": 900,
  "maxCost": 0.2,
  "pipeline": "build",
  "worktree": true,
  "merge": true,
  "baseline": true,
  "policy": ".deus/policy.json",
  "checks": {
    "test": "npm test",
    "typecheck": "npm run typecheck"
  }
}
```

Все поля необязательны. `checks` — именованные команды проверки; массив команд
склеивается через `&&`. Если `checks` нет, раннер ищет `test` в `package.json`.
Файл конфига должен быть закоммичен: `.deus/` целиком в `.gitignore`.

## Пайплайны

| Пайплайн | Шаги | Когда |
|---|---|---|
| `build` | `plan` → `implement` → `review` | Новая фича или изменение |
| `fix` | `investigate` → `fix` → `verify` | Баг с неизвестной причиной |
| `audit` | `survey` → `audit` → `synthesize` | Аудит без изменений в коде |
| `auto` | план от LLM-планировщика | Нестандартная задача |

`plan`, `investigate`, `survey`, `review`, `verify`, `audit`, `synthesize` работают
с запретом на `edit`, `shell` и `subagent`. Реализация (`implement`, `fix`) получает
полный доступ, но её действия ограничены permission-политикой и worktree.

## Планировщик

```bash
npm run v2 -- --cwd /path/to/project --pipeline auto "Перепиши загрузчик конфигов на новый формат"
```

Планировщик — отдельный шаг с агентом `plan`. Он возвращает JSON:

```json
{
  "goal": "переписать загрузчик",
  "steps": [
    { "id": "investigate", "agent": "plan", "mode": "analyze", "task": "найди текущий загрузчик" },
    { "id": "rewrite", "agent": "build", "mode": "change", "task": "перепиши загрузчик" },
    { "id": "review", "agent": "build", "mode": "analyze", "task": "проверь diff" }
  ]
}
```

Ограничения плана:

- 1–8 шагов, уникальные `id`;
- агент только из списка существующих агентов OpenCode;
- `analyze` — только чтение, `change` — правки и команды;
- если есть `change`, последний шаг обязан быть `analyze`;
- свои permission-правила и новых агентов план создать не может.

Посмотреть план без запуска:

```bash
npm run v2 -- --cwd /path/to/project --plan-only "та же задача"
```

План сохраняется в `.deus/runs/<runId>/plan.json` и печатается в stdout. Его можно
поправить руками и запустить (задачу можно не повторять — возьмётся `goal` из плана):

```bash
npm run v2 -- --cwd /path/to/project --from-plan plan.json
```

Невалидный ответ планировщика повторяется дважды с текстом ошибки. После этого
прогон падает, а не подменяется фиксированным пайплайном.

## Проверка результата (gate)

Шаги реализации (`implement`, `fix` и все `change`-шаги плана) помечены `gate`.
Если такой шаг не изменил ни одного файла, он падает с `step produced no changes`:
для change-задачи пустой diff — это не успех.
После шага раннер сам запускает команды проверки из `deus.json` (или
`npm test`, если конфига нет):

- exit code 0 — шаг принят;
- ошибка — раннер запускает шаг ещё раз, приложив вывод упавшей команды;
- по умолчанию две попытки всего, затем прогон падает.

Перед первым gated-шагом раннер один раз запускает проверки на нетронутом worktree —
это baseline. Дальше результаты сравниваются:

- baseline зелёный — любая ошибка блокирует шаг;
- baseline красный, падают те же тесты — шаг проходит с предупреждением;
- появились новые падающие тесты — шаг падает и уходит в retry.

Сравнение идёт по именам упавших тестов в выводе (node:test, jest, mocha, vitest,
pytest, go test). Компиляторные и тулзовые ошибки (`error TS…`, `error[E…]`,
`error:`, `make: *** … Error N`, `ENOENT`, `sh: N:`, `panic:`, `Segmentation fault`,
`Killed`) сравниваются построчно и не прячутся за уже известным падением.
Runtime-ошибки (`AssertionError`, `TypeError`, …) сравниваются по классу: изменившийся
текст ассерта — не новое падение, новый класс ошибки — падение. Любой timeout
считается провалом: прогон, который не успел провериться, не мержится.
Если baseline был красным, запускаются все проверки, а не только первая. Если
текущий вывод не распознан: идентичный вывод считается pre-existing, изменившийся —
падением (сравнить нельзя, поэтому fail-closed). Отключить сравнение:
`--no-baseline` или `"baseline": false`.

Вывод проверок сохраняется в артефакт шага, baseline — в `run.json`.
Отключить проверки совсем: `--no-gate`.

Чего gate не делает:

- не мешает агенту удалить тест полностью — в промпте есть запрет, а review-шаг
  видит diff, но машинной гарантии нет;
- не устанавливает зависимости. В worktree `node_modules` симлинкуется из проекта,
  если git его игнорирует; иначе проверки могут не запуститься;
- не гарантирует распознавание новых падений в нестандартном формате вывода.

## Результат в основном дереве

После успешного прогона worktree коммитится в ветку `deus/<runId>`.

Авто-мерж выполняется, если:

- прогон завершился успешно;
- основное дерево чистое;
- проект не в detached HEAD.

`HEAD` может сдвинуться за время прогона. Если слияние проходит без конфликтов —
оно выполняется сразу. Если есть конфликты, раннер запускает агента `build` в
основном дереве: агент правит только конфликтные файлы, без shell и без коммита.
Технически edit разрешён только на файлы из списка конфликтов; `.git`, `.deus`,
`node_modules`, секреты, webfetch и внешние пути запрещены.
После агента раннер проверяет, что не осталось маркеров и правок вне списка,
прогоняет checks и делает merge-коммит. Если checks создали файлы вне конфликтов,
авто-мерж отклоняется. Любой сбой — `git merge --abort`, изменения остаются в ветке.

Перед мержем проверяется, что проект на той же ветке, что и при старте, история
содержит базовый коммит, дерево чистое, а ветка не трогает untracked-файлы под
ignore-правилами. Иначе раннер не трогает основное дерево и оставляет ветку.
Пустая ветка (коммит не состоялся) не считается влитой: раннер до-коммитит
изменения, а если worktree чист — возвращает `skipped`.

Мерж идёт через `--no-ff`, поэтому весь прогон откатывается одним `git revert -m 1`.
Если авто-мерж выключен или условия не выполнены, раннер оставляет ветку и
печатает команду мержа. Отключить авто-мерж: `--no-merge`.

Код выхода: `0` — успех и мерж выполнен (или изменений нет), `1` — прогон упал,
`2` — прогон успешен, но изменения остались в ветке и требуют ручного мержа.

```bash
npm run v2 -- ...              # авто-мерж при чистых условиях
npm run v2 -- --no-merge ...   # только ветка
```

## Один агент

```bash
npm run v2 -- --cwd /path/to/project --direct --agent build "Почини тест в math.test.js"
```

`--direct` не запускает пайплайн: один шаг, один агент. Результат проверяется
gate, как обычный шаг; отключить: `--no-gate`.

## Resume

Если процесс убит или получил `Ctrl+C`, раннер прерывает активную сессию и пишет
чекпоинт. Продолжить:

```bash
npm run v2 -- --cwd /path/to/project --resume run-20261121T114203
```

Успешные шаги не повторяются. Повторяется только шаг, который был прерван или упал.
Если шаг упал на проверках, при возобновлении в промпт попадает вывод проверок.
Worktree, план и модель берутся из чекпоинта; `--model` можно передать явно.

## Worktree

По умолчанию прогон идёт в отдельном git worktree:

```
<project>/.deus/worktrees/<runId>
```

Это защищает основное дерево от изменений агента. Незакоммиченные изменения в
основное дерево **не попадают** — worktree создаётся от `HEAD`. Если нужен прямой
прогон:

```bash
npm run v2 -- --no-worktree ...
```

`node_modules` из проекта симлинкуется в worktree, если он есть и git его игнорирует:
без этого проверки не найдут зависимости. `--cwd` должен указывать на корень
git-репозитория; подкаталог (monorepo package) отклоняется с понятной ошибкой.

После прогона worktree остаётся для ревью. Изменения уже закоммичены в ветку,
поэтому смотреть их нужно из основного дерева:

```bash
git -C <project> diff <baseCommit>..deus/<runId>
```

`<baseCommit>` есть в `run.json`.

Удалить worktree после успеха: `--cleanup`. Удаление пропускается, если изменения
не удалось закоммитить.

## Permission-политика

По умолчанию раннер разрешает обычные команды и запрещает опасные:

- `git push` (в том числе `git -C … push`)
- `git reset --hard`
- `git clean -f`
- `rm -rf /` (в том числе `rm -rf -- /`)
- `sudo`
- `mkfs`, `dd if=`
- `shutdown`, `reboot`
- `curl | sh`, `wget | bash`
- чтение и правка `.env`, `*.env`, `.envrc`, приватных ключей (`*.pem`, `*.key`, `*.p12`, `*.pfx`) и `.ssh/.aws/.gnupg`
- `env`, `set`, `printenv` через shell
- `webfetch`, `websearch`, `external_directory`

Свой файл: `.deus/policy.json` в проекте, `policy` в `deus.json` или `--policy <file>`.

```json
{
  "default": "allow",
  "rules": [
    { "match": "git push", "decision": "deny", "reason": "push is a human decision" },
    { "match": "npm test", "decision": "allow", "reason": "tests are safe" }
  ]
}
```

Правила применяются по порядку, побеждает последнее совпадение. `match` — регулярное
выражение по строке `action resource`. `deny` отправляется агенту как `reject`,
`allow` — как `once`.

Раннер принудительно переводит `shell` в `ask` на уровне сессии и отвечает сам,
поэтому политика применяется и к агентам, у которых shell разрешён по умолчанию.
То же для чтения `.env`, ключей, `.ssh/.aws/.gnupg` и `webfetch`: они приходят как
`ask` и решаются политикой. `deny` из policy-файла имеет приоритет над разрешениями
агента. Плата за это — до ~250 мс на shell-команду, пока раннер отвечает на запрос.

Широкое правило вида `{"match":".*","decision":"allow"}` перекрывает встроенные
запреты: policy-файл доверенный, но это стоит помнить.

## Чекпоинты и артефакты

```
<project>/.deus/
├── runs/<runId>/
│   ├── run.json          # состояние, шаги, стоимость, план, apply
│   ├── run.md            # сводка
│   ├── plan.json         # план, если работал планировщик
│   ├── planner.md
│   ├── conflict-resolution.md
│   ├── step-00-plan.md
│   ├── step-01-implement.md
│   ├── step-01-implement-attempt-1.md
│   └── step-02-review.md
└── worktrees/<runId>/    # изолированное дерево
```

`run.json` обновляется после планировщика и после каждого шага. Упавшие попытки
gated-шага сохраняются отдельными файлами `*-attempt-N.md`.

## Модель и стоимость

По умолчанию:

```
tokenharbor/deepseek-v4.1-flash:free
```

Бесплатный вариант, стоимость $0. Переопределить:
`--model tokenharbor/deepseek-v4.1-flash#high` (платный) или
`--model opencode-go/deepseek-v4.1-flash#max`.

Провайдер не всегда отдаёт стоимость сессии, поэтому при нулевой стоимости раннер
считает её по токенам и таблице цен (`src/v2/pricing.ts`). Это оценка, а не биллинг.
Стоимость повторных попыток суммируется. Лимит: `--max-cost 0.05`.

## Ограничения текущего среза

- Планировщик недетерминирован: два запуска на одну задачу дадут разные планы.
- Нет параллельных шагов и DAG: шаги идут строго по очереди.
- Сравнение с baseline — эвристика: идентичный нераспознанный вывод считается pre-existing, изменившийся — падением. Нестандартный reporter может дать ложное падение, но не ложный зелёный. Timeout любого check — всегда провал. Fatal-сравнение построчное: изменившееся сообщение pre-existing ошибки считается новым fatal.
- Checks, создавшие неигнорируемые файлы вне конфликтов, блокируют авто-мерж — by design.
- Permission-запрос, на который reply не удался 5 раз, остаётся без ответа и ждёт step timeout.
- Если сессия исчезла до подсчёта, стоимость шага не подтягивается.
- `external_directory: deny` отрезает агенту и глобальные skills/config (`~/.agents`, `~/.config/opencode`).
- Если check делает `git add` вне конфликта, это не видно проверке и может попасть в merge-commit; отменённый merge оставляет untracked-файлы checks в проекте.
- Авто-abort незавершённого merge может отбросить ручные правки, если ты разрешал конфликты, но не коммитил.
- При timeout проверки убивается только shell, дочерние процессы (`npm test` в watch-режиме) могут остаться.
- Стоимость при жёстком падении процесса между шагами может быть недосчитана.
- untracked-файлы не показываются в diff для review (только имена в `git status`).
- Policy-файл с широким `{"match":".*","decision":"allow"}` ослабляет встроенные запреты.
- Секреты и `.env` в worktree не копируются: проверки, которым нужны реальные креды, могут не пройти.
- Разрешение конфликтов делает агент: при противоречивых намерениях он может выбрать неверную сторону. Checks обязательны, review лишь рекомендует — его вердикт не парсится.
- Resolver правит только конфликтные файлы; `.git`, `.deus`, `node_modules`, секреты и внешние пути запрещены. Checks, создавшие файлы вне конфликтов, блокируют авто-мерж.
- Permission-запросы дочерних subagent-сессий не опрашиваются: раннер отвечает только за корневую сессию.
- Ветка `deus/<runId>` после мержа остаётся; удалить: `git branch -d deus/<runId>`.
- KB/smart-context из старого deus не подключены к V2-раннеру.
- Сессии по умолчанию сохраняются для отладки. Их можно удалить через TUI/API.

## Тесты

```bash
npm run typecheck
npm test
```

Юнит-тесты покрывают порядок шагов, подстановку `{task}/{prev}`, resume, лимит
стоимости, abort, permission-политику, конфиг, baseline и retry, планировщик,
идемпотентный apply и разрешение конфликтов.
Реальный smoke:

```bash
npm run v2:smoke
```
